# Threat model

Scope: the shipped app (`app/`, `sidecar/`, `core/`) running on one user's machine, reading documents the user chooses to open. Design background is in `privacy.md` and `architecture.md`; decisions are D-06 (Electron + sidecar + llama.cpp), D-09 (model download is the only network path) and D-65 (security baseline).

Status values: **done** (built and checked), **test only** (a test enforces the rule on today's code, the feature it guards is not built yet), **not built yet, Phase N** (planned, no code or test).

Test names below are in `tests/test_security_static.py` (`static:`) or `tests/test_import_boundaries.py` (`boundary:`). Rule names `net`, `shell`, `unsafe`, `bind` are the static test's rules.

## What the static tests cover and do not

`tests/test_security_static.py` reads `.py` files in `core/`, `sidecar/` and `app/` with `ast`. It follows `import x as y` and `from x import y` so an alias does not hide a call. It does not run code, and it does not read TypeScript, so the Electron rules in rows 1 and 3 need their own test when `app/` exists. It cannot see a host chosen at runtime (`host=some_variable`) or a module loaded by string; the boundary test bans dynamic imports for that reason. The `bind` host check looks at `host=` keyword arguments and at string constants, not at positional arguments. Allowlist entries (`ALLOWLIST` in the test file) need a written reason, and a rule is relaxed only for the named file.

## What we cannot promise

- A compromised or malicious operating system, a keylogger, a screen recorder, a malicious browser extension or another process running as the same user can read documents, memory and the keychain regardless of what Shiori does.
- Someone with the user's unlocked session can open every document the app can open.
- The network is outside the app. Shiori makes no requests after model setup, but it cannot stop the OS, a VPN, a proxy, or other software from seeing that the machine is online. Packet capture on a trusted machine is how the claim is checked, not a proof that holds on every machine.
- Hardware and firmware attacks, cold-boot memory reads and swap files are not addressed. The OS may write memory to swap; full-disk encryption is the user's job.
- Deleted data on an SSD may survive in blocks we cannot overwrite; crypto-shredding (destroy the key) is the mitigation, and it only protects documents stored with a key.
- A bug in a dependency we have not found yet. Pinned versions, audits and the sandboxed parser reduce the chance and the damage, they do not remove it.
- The model can be wrong. Code checks that a cited sentence contains the value; it cannot check that the Japanese meaning was understood correctly.
