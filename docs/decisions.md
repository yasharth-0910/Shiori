## D-01: Solo project, separate from Klaro
Date: 2026-10-02
Status: accepted
Context: The team major project (Klaro) is a general local RFP analyzer. This project is Japanese-specific and built alone.
Decision: Fresh repo, fresh code. No code from the Klaro repo. Japanese-specific handling is the center of the project.
Consequences: Clear ownership in interviews. Some overlap in concept, so the differentiation must be visible (Japanese rules, citation verification, benchmark).

## D-02: Extraction with citations, not full translation
Date: 2026-10-02
Status: accepted
Context: Users of a 60-page tender need about 10 facts and proof of where each came from, not a full translation.
Decision: Core output is structured fields + executive summary, each linked to source sentences. Translation is on demand for single sentences.
Consequences: Smaller model inputs, measurable accuracy, trustable UI.

## D-03: Model cites sentence IDs, code maps to pages and boxes
Date: 2026-10-02
Status: accepted
Context: LLMs guess page numbers badly.
Decision: The model receives numbered sentences and returns sentence IDs. Pages and bounding boxes come from the extractor.
Consequences: Extractor must produce stable IDs; labels are tied to extractor version.

## D-04: Verify every citation before display
Date: 2026-10-02
Status: accepted
Decision: A field is shown as found only if code confirms the value appears in a cited sentence. Otherwise "not found".
Consequences: Some correct answers will be rejected (tracked as verifier false rejects). Wrong answers with highlights become rare.

## D-05: Scope v1 to Japanese public tenders
Date: 2026-10-02
Status: accepted
Context: Real corporate RFPs are confidential and unavailable for training or eval.
Decision: v1 handles public Japanese government tender bundles (notice, bid instructions, spec). Corporate RFPs, contracts, other languages come later on the same pipeline.

## D-14: Collection respects robots.txt, site terms and form walls
Date: 2026-10-02
Status: proposed
Context: The Phase 1 source survey (`data/manifests/source_survey.md`) found that some sources forbid crawling, and that the full bid documents for national tenders sit behind a contact-details form on GEPS.
Decision: Automated collection skips any path robots.txt disallows for `*`, and any site whose terms forbid crawlers, even when the content is free to read. As of 2026-10-02 that excludes Kanpo (robots.txt and its terms both forbid crawlers), the 官公需情報ポータルサイト (`Disallow: /`) and the Tokyo e-procurement system. The collector never fills in the GEPS 連絡先情報 form. A site that returns 403 to our honest User-Agent (JPO) is not retried with a different one. Documents from these places can still enter the corpus if Yasharth downloads them by hand in a browser, with a manifest row that records that.
Consequences: National-ministry bundles (入札説明書 + 仕様書) must come from agencies that post them on their own sites, or by hand. Local governments supply most of the automated bundles.

## D-15: GEPS bid documents are out of scope
Date: 2026-10-02
Status: accepted
Context: The bid documents (入札説明書, 仕様書) for national 一般競争 tenders are served by GEPS only after a 連絡先情報 form (company, person, email, phone) is filled in. D-14 already stops the collector from filling it in, and left open whether a manual download was acceptable.
Decision: GEPS documents are out of scope. We don't fill in its form, manually or automatically.
Consequences: Closes the GEPS open question. National bundles come only from agencies that post documents on their own sites (Digital Agency 公募 and RFI pages, for example). p-portal still supplies notice text (D-18).

## D-16: Every document gets a license class
Date: 2026-10-02
Status: accepted
Context: Sources differ in what they allow. PDL1.0 and 政府標準利用規約 2.0 are CC BY 4.0 compatible; Funabashi City and JETRO reserve all rights. Phase 9 plans to publish the eval set, so we need to know per document what may be published.
Decision: Each manifest row has `license_class`:
- `open`: PDL1.0, 政府標準利用規約, or anything CC BY compatible. May go into a published eval set.
- `restricted`: all rights reserved (e.g. Funabashi). Used only locally for training and dev, never published.
- `unknown`: treated as `restricted`.
The class is set per source in the adapter, from the terms page recorded in `license_note`.
Consequences: The published eval set (Phase 9) is drawn from `open` documents only. Whether training on `restricted` documents is fine under Japanese copyright law Art. 30-4 is still an open question below; until it is answered, `restricted` files stay on this machine.

## D-17: Sites that block our User-Agent are skipped
Date: 2026-10-02
Status: accepted
Context: JPO returns 403 to every request from `ShioriResearchBot/0.1`, robots.txt included.
Decision: If a site blocks our User-Agent, we skip it. We never retry with a browser User-Agent or any other workaround. The collector's HTTP client never retries a 403 and stops the run for that source.
Consequences: JPO stays out of the corpus. The JPO open question (bot block or IP block) no longer affects collection.

## D-20: Tender pages whose HTML is the notice are saved as html notices
Date: 2026-10-02
Status: accepted
Context: On Digital Agency 公募 detail pages, the 公募公告 is the page text itself; only 応募要領, 様式, 契約書（案） and 仕様書 are PDFs. Funabashi tender pages work the same way: the page is the 公示, and the PDFs are 実施要領, 評価基準, 仕様書 and results. Without the page, no bundle from these sources would contain a notice.
Decision: The collector saves the tender page itself as a document with `doc_type: "notice"` and `format: "html"`, raw bytes as served, hashed like any other file. It goes in the same bundle as the PDFs. Like D-18, html documents are scored without highlights.
Consequences: Bundles from these sources can count as complete (notice + spec). The saved pages include site navigation, so the HTML text path must pick the article or main element. Funabashi pages are updated after the tender (results, Q&A), so the saved notice reflects the page on the day it was fetched.

## D-21: PDFs inside ZIPs are extracted, each with its own manifest row
Date: 2026-10-02
Status: accepted
Context: Some tenders post their documents only as a ZIP (Funabashi's homepage rebuild, p146651, is one 7 MB ZIP). Skipping ZIPs loses whole bundles.
Decision: The collector downloads a ZIP that belongs to a bundle, gives the ZIP itself a manifest row (`format: "zip"`, so every downloaded file has a row), and gives each PDF inside its own row with `extracted_from` set to the ZIP's doc_id. Extracted PDFs join the bundle; the ZIP does not. docx and xlsx inside ZIPs are skipped for now. Safety:
- Members are read in memory and written under their SHA-256, never under their own path, so a zip-slip name can't write outside `data/raw/`. Members with absolute paths or `..` are skipped anyway.
- A ZIP whose members would expand past 200 MB in total is skipped whole. zipfile stops reading a member at its declared size, so a lying header can't get past the check.
- Encrypted members are skipped.
- Member names without the UTF-8 flag are decoded as UTF-8, then CP932 (Japanese Windows), since zipfile would read them as CP437 mojibake (TXT-8).
Consequences: A ZIP counts as one file against `--limit`, however many PDFs it holds. The PDFs' `url` is `<zip url>#<member name>`, which is not fetchable on its own; `extracted_from` is the real provenance. First real ZIP (Hokkaido, city survey, 2026-10-02): 4 PDFs extracted, 10 docx skipped. Its names had the UTF-8 flag, so the CP932 path is still tested only offline. After part D: 16 ZIPs, 160 members, 34 PDFs extracted. 24 member names had no UTF-8 flag (Okayama) and decoded correctly as CP932, e.g. `1_公告（岡山芳泉）`.

## D-22: Restricted and unknown documents are used locally, never redistributed
Date: 2026-10-02
Status: accepted
Context: Most local governments reserve all rights (city survey: about 4 of 130 are open). Without them the corpus can't reach 15+ issuing organizations, and an org-level split (D-07) needs many organizations.
Decision: Documents with `license_class` `restricted` or `unknown` may be used locally for analysis, training, dev and test, on the basis of Japan's Copyright Act Article 30-4 (use for information analysis). They are never redistributed: no PDFs, extracted text, or labels containing source spans from them go into any public repo, dataset or release. A published benchmark uses only `open` documents. robots.txt and D-17 still apply regardless of license, so Kurashiki's attachments, which its robots.txt disallows, stay off-limits.
Consequences: Train, dev and test may all contain restricted organizations, so the internal split doesn't have to be drawn from open organizations only. A public benchmark in Phase 9 is a separate, open-only subset, and its numbers have to be reported separately from the internal test numbers. Article 30-4 has a proviso: it doesn't apply where the use would unreasonably prejudice the copyright holder's interests. This is Yasharth's reading, not legal advice. Anything that leaves this machine needs a license check per document. Labels (`data/eval/`) are committed to git, so labels for restricted documents must not contain source text if the repo is ever made public (see open questions).

Date: 2026-10-02
Status: accepted
Context: Labels hold source spans (`value_ja`, cited sentences). D-22 forbids redistributing text from `restricted` and `unknown` documents, but `data/eval/` is committed, so its labels would leave the machine as soon as the repo is pushed anywhere public.

## D-25: p-portal notices are filed under the 調達機関, original notice only
Date: 2026-10-02
Status: accepted
Context: The p-portal adapter (D-18) needs an `issuer_org` for the org-level split (D-07), and a notice can have corrections (訂正公告) and cancellations (取消公告).
Decision: `issuer_org` is the 調達機関 field of the notice page (a ministry or agency such as 総務省 or 国土交通省), not the office named in the notice body (a regional bureau, for example). Regional offices of one ministry are likely to share templates, so filing them under the ministry keeps them on one side of the split. Only the original notice is saved (permalink with `chankbn=0&chancnt=0`); corrections are not. Search covers active 一般競争入札 notices (WTO and non-WTO, p-portal types 05 and 10), IT titles first, at most 8 per 調達機関, round-robin across organizations. `wto_covered` comes from the notice's 調達種別, `has_english_summary` from a line starting with `Summary` in the notice body. Notices whose body is under 200 characters are skipped: in the first dry run about 20 of 122 were stubs such as 別添のとおり ("as attached"), with the real notice in an attachment on GEPS (D-15). The cap counts kept notices, so a skipped stub frees its org's slot.
Consequences: p-portal notices from デジタル庁 join the same org as the `digital` source, which is what the split needs. 気象衛星センター (JMA samples) is part of 気象庁; if p-portal brings 気象庁 notices, the two names must be merged before the split is drawn (open question). A notice that was later corrected is stored in its original wording, so labels must not take values from the correction.

## D-27: is_it uses a strict cue list
Date: 2026-10-02
Status: accepted
Context: The part E cues (運用, 保守, 構築 and others) also matched elevator, air-conditioning and copier maintenance, so every p-portal notice counted as IT. IT counts need one definition before they are quoted.
Decision: The manifest field `is_it` is true when the document's title or the title of a bundle it belongs to contains one of システム, クラウド, ソフトウェア, データ, 開発 (`STRICT_IT_CUES` in `collector/collect.py`). ## D-29: Extractor output: displayed-page coordinates, only real characters
Date: 2026-10-02
Status: accepted
Context: The viewer (PDF.js) draws highlights from stored boxes, and labels point at text whose characters must match the PDF exactly (TXT-2).
Decision: (1) Every box is in PDF points on the page as displayed, after /Rotate, origin top-left, y downwards: the same frame as PDF.js at scale 1, so the viewer never handles rotation. (2) Text comes from MuPDF with `TEXT_INHIBIT_SPACES`. By default MuPDF inserts a space wherever two glyphs have a gap; those spaces are not in the PDF and were the cause of the JMA `1 6 日` case (TXT-9). With the flag, a line's text is exactly the characters the PDF draws, real space glyphs included. (3) Private Use Area characters that MuPDF drops because they have no box (a 外字 drawn as an image with /ActualText, TXT-12) are put back with an estimated box (`pdf._recover_pua`). (4) Lines are flagged, never deleted (headers, footers, page numbers, vertical text); `EXTRACTOR_VERSION` in `models.py` is bumped whenever chars, lines, line IDs or page kinds change.
Consequences: TXT-9 shrinks to the spaces that really are in the PDF (digit-unit gaps in Word exports). English pages read normally (`Cabinet Order`, not `C a b i n e t O r d e r`). Any future backend must reproduce (2) and (3), or labels made against one extractor version won't match another.

## D-30: Only page numbers and page-wide repeats are left out of sentences
Date: 2026-10-02
Status: accepted
Context: Segmentation needs a rule for which flagged lines to drop. Phase 2 part A flagged a line as header/footer when it repeated at the page edge on 3+ pages and 30% of the document, which also caught table header rows repeated on continuation pages (doc `3fc2a22e...`, Okayama: `項  目 | 必要とする数値等`) and the title block of engineering drawings (doc `69bb4a0580c8...`, Niigata).
Decision: A line is left out of sentences only if it is flagged `page_number`, or flagged `header_footer`: the same text (spaces ignored) at the same place in the top or bottom 12% band on at least 3 pages and at least half of the document's pages. A line inside a ruled table cell (D-31) is never `header_footer`, so repeated table header rows stay in. Flags are still never deleted from the lines, only skipped by `segment`.
Consequences: Corpus (322 PDFs): 991 page-number lines and 43 header/footer lines left out, down from 196 header/footer lines under the 30% rule. Real cases: `（案）` on all 17 pages of doc `75a0c52799f9...` (Digital draft contract) and `＜別添２＞` on all 18 pages of doc `133bbf881b4d...` (Nara) are left out; the Okayama table header and the Niigata drawing title block stay in, as table sentences. Fixtures and tests: `digital_draft_header.pdf`, `okayama_table_spec.pdf`. Documents under 3 pages never lose a header.

## D-31: Ruled tables come from MuPDF's find_tables, one-row tables ignored
Date: 2026-10-02
Status: accepted
Context: TXT-6 splits sentences at table cell boundaries, and D-30 needs to know which lines are in a table. The extractor groups lines but knows nothing about tables.
Decision: `PdfFile.table_cells` calls PyMuPDF's `find_tables()` (default strategy: drawn cell borders) on text and mixed pages, and keeps the cells of tables with at least 2 rows. Each line gets the smallest cell that holds its center (`Line.cell`). No new dependency: it is part of PyMuPDF (D-28), behind the same module.
Consequences: About 13 ms per page. Of 657 tables found with 2+ cells, 80 have one row; some of those are drawn from invisible objects around a plain heading (doc `fb226cbdd14b...`, Hokkaido p2: `(4) 入札金額等に係る...` came out as a three-cell table), and the cells of a real one-row table are separate lines anyway. Tables without drawn borders are not detected; their cells stay separate lines because the extractor does not join across wide gaps, but they are not marked `in_table`. 32% of all sentences are in table cells, mostly in narrow cells; the documents that are 80%+ table are Q&A sheets, evaluation criteria and results. A pypdfium2 backend (D-08) would need its own table finder.

## D-32: Sentences and section paths
Date: 2026-10-02
Status: accepted
Context: Labels, retrieval and citations all point at sentence IDs (D-03), so the segmentation rules and the ID scheme need to be written down. Rules are in `core/shiori_core/segment.py` and `normalize.py`; this records the choices behind them.
Decision:
- A sentence's `text_orig` is its line spans joined with nothing in between, leading and trailing spaces of each line dropped. Japanese wraps without spaces, so this is right for Japanese; wrapped English loses the space at the line break (known limit). Each span keeps its line ID and character offsets (`LineBox`), so any character of `text_orig` maps back to a glyph box.
- IDs are `p{page}_s{n}`, `n` counted per page over sentences that start on that page. A sentence that runs onto the next page keeps the ID of its first page and has boxes on both.
- Lines join when the previous one reaches the right margin (or the edge of its cell) and the next sits right under it, not left of where the previous line started; or when the next line starts with hiragana or closing punctuation; or when the next line touches the previous one on the same baseline (a visual line the extractor cut in two). A blank line breaks a sentence except at a page break. List markers, `記`/`以上` lines, table-of-contents entries and cell boundaries always break.
- Markers are detected on the original line before NFKC (TXT-3, TXT-13). Styles: `第N`/`第N章`/`第N条`, `1`/`1.`, `1.1` (by depth), `(1)`/`⑴`, `①`, `ア`, `(ア)`, `㋐`, `a`, `(a)`, `一`, `Ⅰ`, `(ⅰ)`, and bullets (`・ ● ○ ◎ ■ ※`, PUA). Bullets split sentences but open no level.
- Levels are assigned by order of first appearance, not by a fixed hierarchy: a new style goes one level down, a style already on the stack closes everything below it. A new level must start at 1 (bare numbers also at 2, for law-style paragraphs). A sibling may go back but not jump more than 2 ahead. `記` and `以上` reset the stack. Numbering inside a table goes on a separate stack appended to the body path and dropped when the table ends.
- Circled numbers and circled katakana are kept out of NFKC in `text_norm`; TXT-14's six read-off mappings are applied to every document, since those Extension A and Phonetic Extensions code points don't occur as real text in tenders; TXT-9 also removes the space between an era name and a digit.
Consequences: Over the corpus, 49,312 sentences, 88% with a non-empty section path (`data/manifests/segmentation_report.md`). Known limits, also in the open questions: two-column pages interleave (4 Okayama pages); contract article titles such as `（契約期間）` come before `第２条` and get the previous article's path; a cover sheet's numbering carries into the notice that follows (doc `2aa7506afc08...`, JMA, D-19) until the notice's first marker; `1`-level headings missing from the text layer (Word auto-numbering, doc `756d17c84006...`) leave their content under the previous number.

## D-33: Value converters return a span and never guess
Date: 2026-10-02
Status: accepted
Context: Verification (D-04) compares normalized values, so the converters decide what counts as a date or an amount.
Decision: `value_normalize.find_*` take `text_norm` and return every match as `Found(start, end, text, value, reason)`. When a match can't be turned into a value without assuming something, `value` is None and `reason` says why: no year, year and month only, blank form field, weekday mismatch (DATE-5), before or after an era (DATE-3), ambiguous 午前0時 / 午後12時, 24:00, placeholder amounts (`●円`, `〇〇円`), bad thousands separators. A month-day date never borrows the year of an earlier date in the same sentence. Deterministic readings are converted: `令和9年3月末` -> 2027-03-31, `令和8年度末` -> 2027-03-31, `令和4・5・6年度` -> 2022-04-01 to 2025-03-31, `1,100千円` -> 1,100,000. Tax wording is classified per phrase (`tax_included` / `tax_excluded`); which amount it belongs to is for `locate` and `llm_extract` to decide.
Consequences: Corpus: 1,387 of 1,787 date matches convert, 539 of 541 fiscal years, 646 of 646 times, 214 of 256 amounts. Most failures are honest: 171 year-and-month dates, 118 month-day dates without a year, 107 blank form dates, 39 blank or placeholder amounts. Five dates in five documents have the wrong weekday in the source (for example `令和8年3月3日(水)` in doc `4a654d8861b5...`; 3 March 2026 is a Tuesday), so the documents disagree with themselves and a label has to say which part is right. (Superseded by D-38: such a date now returns its value with a warning holding both readings.)

- Runaway arrays: LFM2.5-1.2B-JP listed sentence IDs until the 300-token limit and produced cut-off, invalid JSON. Adding `maxItems: 5` to the schema fixed it, but it then often filled all 5 slots (6 of 8 runs) with neighbouring IDs.
- Contradictory fields: LFM2.5-1.2B-JP set `found: false` while also filling `deadline_text` with a date in 5 of its 8 runs. A rule such as "found false means no value" has to be enforced in code, not trusted.
- Invented or malformed IDs: Qwen3.5-4B and Qwen3.5-9B each cited an ID that does not exist for the WTO notice (`[h_22]`, `h_22`; the real one is `h_s22`), LFM2.5-1.2B-JP cited IDs that do not exist on the notice (GPU and CPU runs) and LFM2.5-8B-A1B on one CPU run, and LFM2.5-1.2B-JP wrapped IDs in brackets (`[p1_s4]`). The ID check must reject these rather than guess.
- Not verbatim: Qwen3.5-4B and Qwen3.5-9B rewrote the quoted date (full-width digits turned to half-width; spaces inserted, `令和 8 年`). Verification must compare normalized text with the offset map back to the original, never the model's string.

I cannot judge which is right (open question below).
- Output route: Sarashina2.2-3B's community GGUF (March 2025 conversion) emits a literal `</s>` that llama-server's chat parser rejects when a JSON schema is set (HTTP 500). Applying the chat template by hand and calling `/completion` with the same schema works, and its rows in the report are marked `completion`. Using it in the app would mean owning that route.
- Thinking switches: `--reasoning off` stops thinking on the Qwen3.5, Gemma 4, Swallow, Nemotron and LFM2.5-1.2B runs but is ignored by LFM2.5-8B-A1B, whose trace used all 300 tokens and left the answer empty. `--reasoning-budget 0` works for it. Any model added later needs this checked.

Caveats: one prompt per document, run once, so speeds carry run-to-run noise that was not measured; the full pipeline (extract, locate, verify) was not timed; the Mac's CPU is not a Windows laptop CPU; all but three GGUFs are third-party conversions (sources.md); `ids exist` in the report only checks that cited IDs are in the document.
Consequences: Phase 4 accuracy work starts with LFM2.5-1.2B-JP (floor), LFM2.5-8B-A1B, Qwen3.5-4B and Gemma 4 E4B as the models that can plausibly ship on a 16 GB laptop, and with Qwen3.5-9B, Swallow 8B and Nemotron 9B as Mac-only upper references. The prompt design should keep inputs to the located sentences (a few thousand tokens), and the verification step must treat model output as untrusted text.

- Runtime dependencies added to `[project].dependencies`, with versions and licenses as installed: `onnxruntime` 1.23.2 (MIT; the version NDLOCR pins for macOS; brings coloredlogs MIT, humanfriendly MIT, flatbuffers Apache-2.0, protobuf 7.36.2 BSD-3-Clause, sympy BSD with mpmath BSD), `opencv-python-headless` 5.0.0.93 (Apache-2.0; its wheel bundles library binaries under other licenses, including one under the GNU LGPL, text in the wheel's `LICENSE-3RD-PARTY.txt`: review in Phase 8), `numpy` 2.5.3 (BSD-3-Clause and others), `pillow` 12.3.0 (MIT-CMU), `lxml` 6.1.3 (BSD-3-Clause), `pyyaml` 6.0.3 (MIT), `tqdm` 4.70.1 (MPL-2.0 and MIT), `networkx` 3.7 (BSD-3-Clause). Consequences (all numbers in `data/manifests/ocr_report.md`; rendered 200 dpi pages, so an upper bound for real scans):
- Speed: about 4 s to load the models once, then 1 to 2 s per page on the MacBook Air M4 (1.2 s and 2.3 s on two timings of the same 5 pages, 2 s averaged over the 200-page run).

## D-37: HTML notices are anchored by character offsets; English text is marked, not parsed as Japanese
Date: 2026-10-02
Status: accepted
Context: p-portal notices and local-government tender pages are HTML (D-18, D-20): no PDF, so no boxes to highlight. WTO notices end with an English Summary (DOC-3, D-26), which section numbering and the date and amount converters must not read as Japanese.
Decision:
- `core/shiori_core/html_ingest.py` (`load_html_document`, standard library `html.parser` only; BeautifulSoup stays dev-only, D-12) extracts text from the main element of the page: the first of `#main_body`, `<main>`, `<article>`, `.boxEntryBody`, `#content`, `#main`, `<body>` that exists in the page (the list covers the 10 sources in the corpus). Navigation, footers, scripts, hidden elements are dropped; white space is collapsed; every element boundary and `<br>` is a line break. The extracted text is stored on `Document.text` (`format: "html"`, `pages` empty).
- A sentence has `anchor: TextAnchor(start, end)`, offsets into `Document.text`; `Document.text[start:end]` is `text_orig`, except that a sentence joined across a `<br>` has the line break inside the slice. `boxes` is empty, `page` is 0, `source` is `html`, IDs are `h_s{n}` over the document (the scheme the feasibility run already used). The app highlights the offset range in a rendering of the stored text, not in the original page.
- Sentences come from the same segmenter as PDFs (`segment(..., soft_breaks=...)`). In HTML mode lines join only across a `<br>` inside one element, and only by the text rules: next line starts with hiragana or closing punctuation, the sentence has an unclosed bracket, or the next line starts in lowercase Latin after a line ending in a letter or comma. Across an element boundary lines never join, so a heading followed by a paragraph that starts with hiragana stays two sentences. The geometry the segmenter wants is invented (one row per line, one point per character) and ignored in this mode.
- `Sentence.language` is `ja` or `en`. A heading whose text after the marker is `Summary` (`５ Summary`, `14 Summary`) starts an English section: that sentence and every later one is `en` and carries the section path of the Summary heading only, ignoring its own numbering (`(1) Contracting entity` stays under `["5"]`), until a sentence that is mostly Japanese comes back. Without a heading, a sentence is `en` when it has no Japanese character, no `@`, `/` or `_`, at least three words of two or more Latin letters of which two have a lowercase letter, and letters are at least half its characters (`FAX 073-423-3502`, `TEL 03-XXXX-XXXX` and URL paths are not). Its numbering works as for any sentence: a Latin heading such as `10 SLA(Service Level Agreement)` still opens a level. Value converters skip `en` sentences.
- Stub notices (`別添のとおり`) and pages with no readable text give a document with zero or few sentences, never an error.
- Segmenter changes found in review, in the same pass: where two joined lines meet and both sides are Latin letters or digits, `text_norm` gets a space that maps back to the line break (`Japan` + `TEL`); a sentence continues onto the next line when it has an unclosed bracket or the next line starts in lowercase Latin after a letter or comma (Wakayama `2f2f5bd3...` p3 and p4). A fused heading and body (`(10)入札の取りやめ又は延期この入札は…`, Hokkaido `fb226cbd...`) is not split: see open questions.
Consequences: HTML documents have no page highlight; labels and the eval harness score them on field values and cited sentences only (D-18 already says so). Sentence IDs of PDFs change where the new join rules fire, so `EXTRACTOR_VERSION` is 0.3.0. 181 HTML files in the corpus all load. The container list is tuned on these sources and will need a new entry for a new site. Known limits: a weekday after a `<br>` (`令和４年12月27日` / `（火）14時`) is split from its date (open question); table rows are one line per cell, so label and value are two sentences.

## D-38: A weekday that disagrees with the date returns the date with a warning

## D-39: Field schema v1.0.0 is frozen
Date: 2026-10-02
Status: accepted
Context: Labels point at fields, so the field list must stop moving before labeling. The Phase 2 open questions and a review of two real notices (Hokkaido `fb226cbd...`, Wakayama `2f2f5bd3...`) showed the draft could not hold what the documents say.
Decision: `schema_version` 1.0.0, in `docs/field_schema.md` and `core/shiori_core/fields.py` (23 fields), with `tests/test_fields.py` failing when the two disagree on field ids or `applies_to`. Changes from the draft, and why:
- `submission_deadline`, `bid_opening`, `question_deadline`, `briefing_session` became one list `deadlines`, each item a `kind` (bid_in_person, mail_arrival, electronic, bid_opening, question, briefing, document_request, other) with a datetime or relative text and flags. One notice has several (Wakayama: in person 2026-10-27 14:00, mail arrival 2026-10-26 17:00, questions 2026-10-01 17:00). In-person tenders have no 受領期限, so their 入札日時 is a `bid_in_person` deadline (Hokkaido).
- `submission_method` became `submission_modes` plus `mail_not_allowed` (Hokkaido: 認めない).
- Bonds became `{status: required | waived | waived_with_proviso | not_stated, rate_percent}` (Wakayama requires at least 5% and 10%; Hokkaido waives with a proviso).
- `spec_access` added (public, email_after_pledge, at_counter, see_other_document, not_stated): Wakayama gives the spec by email after a pledge.
- Field status is `present`, `absent` or `see_other_document` with a `ref` (spec, bid_instructions, other_notice, kokuji, other). `not_stated` and `see_other_document` inside a value are extractor output only; a label uses the field status, so each fact has one spelling.
- `applies_to` per field. A field that does not apply to a document's type is labeled `absent`, which counts toward the hallucination rate. v1 labels notice, tender_page, bid_instructions and spec; the notice-like types share one list, spec documents carry only title, issuer, scope, period, delivery date and place.
- `tax_basis.unknown` dropped (absent says the same). `wto_covered` is present only when the text says so, `true` or `false`; silence is absent.
- Cues added from the two notices: 入札日時, 入札場所, 郵便等による入札の可否, 認めない (deadlines, submission_modes), 暴力団関係事業者, 指名停止 (eligibility). 前金払 and 契約書作成 belong to no v1 field and are kept as unmapped cues.

## D-43: Silver-label pipeline design
Date: 2026-10-02
Status: accepted
Context: Part B turns the label set into silver labels with two cloud labelers and automatic checks, and sends only what is doubtful to a reviewer (a chat with a Japanese reader). Code: `eval/silver/`.
Decision:
- **One call per document and provider** asks for every field that applies to the document's `doc_type`; the others are written `absent` by rule (`pre_labelers` empty, state `silver_unreviewed`, check `field_not_applicable_rule`). Input is the Japanese sentences only, `<id> | <section_path> | <text_orig>`, with the field list, heading cues and rules (cite Japanese ids only, absent vs see_other_document, SEM-3, DATE-5, DATE-6, NUM-6, DATE-8) and a line saying the document is untrusted data. English Summary sentences are never sent; they feed `en_summary_agrees`. Temperature 0; `prompt_version` `sv1` is in every label's provenance. The answer is JSON in each provider's strict JSON-schema mode: `normalized` travels as a JSON string and empty string means none, so one portable schema serves both providers and the code validates each field against `fields.py`. Each field also gets a one-sentence `reason`, kept only in the raw cache. Line citations of list fields are computed as the union of their items' (the model is not asked to keep two copies in step).
- **Long documents** are split by top-level section into chunks that fit the provider's per-request cap (Groq: 8,000 tokens including the prompt overhead and the output allowance), whole sections packed together, an oversize section cut between sentences with a 2-sentence overlap. Tokens are estimated high (1 per non-ASCII character); the usage ledger records the real counts so the factor can be checked after the pilot. Chunk answers are merged per field: a value in any part beats absent; list fields are unioned; two different values make the field fail `schema_valid` and be flagged.
- **Cache** `data/cache/labeling/raw/<doc_id>/<provider>__<model>__<prompt>__<extractor>__<schema>.json`, written after every chunk, so a re-run costs nothing and a run stopped by a daily cap resumes. Gitignored (it holds restricted-document text). Invalid JSON: retried once, then recorded as a failure (`--retry-failed` asks again). Rate-limit 429: wait and retry up to 3 times. Daily-quota 429, or the ledger reaching the day's requests or tokens: stop that provider for the day.
- **Auto checks** (each `{name, passed}` in provenance). Blocking: `schema_valid`, `citations_exist`, `value_in_citation` (value_ja, and list item text, found in the cited sentences after normalization, spaces ignored), `values_roundtrip` (dates, times, rates, tax wording, arrival flags, codes, grades, phone and email re-run through the converters, via `validate_labels.check_values`), `field_applicable`, `era_plausible` (a date more than 5 years from the manifest notice date), `weekday_consistent` (DATE-5: the label's date is one whose written weekday disagrees). Soft: `heading_cue`. Informational: `en_summary_agrees` (bid-deadline dates, emails, phones, and ASCII tokens of the title against the English Summary). A reviewer's answer on import must pass the first four ("hard") only; the others are recorded.
- **Agreement**: status equal first; then enums, bools, statuses, codes and dates exactly; text fields when citations overlap and `difflib` ratio on normalized text is at least **0.85** (0.60 for `scope_summary`); list fields when every item has a distinct partner (deadlines: kind, datetime, flags, overlapping citations; eligibility: kind, polarity, overlapping citations, text ratio 0.60; required documents: overlapping citations, name ratio 0.85). `value_en` is never compared.
- **Resolution**: both agree and no blocking check fails: accepted, `silver_consensus`. Otherwise flagged. Both absent while a heading cue of the field (in a section title or the first 20 characters of a Japanese sentence) is in the document: flagged. A seeded 5% of accepted fields (seed 20261004, hash of doc id and field) also go to the review export as "consensus spot-check"; the reviewer's answers give a silver error estimate in `status`. Accepted lines are kept in `data/cache/labeling/resolved/`; the label file is written to `data/eval/<split>/labels/` for open documents and `data/eval_private/...` for the rest (D-24) once all 23 fields of a document are resolved, because the validator requires a complete file. Flagged and spot-check items wait in `flagged.jsonl`. A re-run never replaces a reviewed line.
- **Review**: `export` writes `batch-NN.md` (at most 12 items and 25,000 characters, tier 1 fields first, answer format at the top, source sentences with 2 neighbours each side), `import` takes one line per item (`accept A|B`, `absent`, `custom | status= | value_ja= | value_en= | cites= | normalized= | note=`; `normalized=` is an addition to the brief's format because structured fields cannot be built without it). One malformed line imports nothing. Imported labels are `reviewed_by claude_chat`, `silver_model_reviewed`; never `human_audited` (D-41).
- **Quota guard**: `plan` prints documents, calls, estimated tokens, split documents and days of free quota per provider. `run` needs `--yes` and `--max-calls N`, prices the remaining work with the same code, and aborts if it passes N calls or a provider's requests/day or tokens/day. The test split needs `--allow-test` and is for the end, with the frozen prompt version.
- Provenance gained two fields (`prompt_version`, `labeler_overlap`). Nothing under `core/` changed; `EXTRACTOR_VERSION` stays 0.3.0.
Consequences: Plan output on 2026-10-02 (estimates; output tokens assume every field is answered with a reason, so they run high): **pilot** (5 open dev documents): Gemini 5 calls, ~27k in, ~15k out; Groq 12 calls (4 documents split), ~41k in, ~35k out, 1 day. **Dev** (60 documents, 37 open): Gemini 37 calls, ~216k in, ~112k out, 1 day (assumed limits); Groq 193 calls (48 documents split), ~671k in, ~570k out, **7 days** at the 200,000 tokens/day cap; local Qwen3.5-9B for the 23 restricted documents' Gemini slot, 23 calls, ~183k in. **Test** (40 documents, 30 open): Gemini 30 calls, ~194k in, ~87k out, 1 day; Groq 118 calls (29 split), ~429k in, ~332k out, **4 days**; local 10 calls, ~85k in. Groq's 8,000 tokens per minute is the bottleneck: the rules and field list cost about 2,200 tokens per call, so a notice needs 2 to 3 chunks. Not yet measured: whether the real answers are as long as estimated, and whether Groq's strict schema mode accepts this schema (no labeling call has been made).

## D-46: Silver pipeline v2 (prompt sv2), from the pilot review
Date: 2026-10-03
Status: accepted (code and tests; the sv2 pilot waits for Yasharth's go-ahead)
Context: The sv1 pilot (`eval/reports/silver_pilot.md`) flagged 36 of 69 decisions on 3 documents, and the review of 37 items (`pilot-all.txt`) showed why: about 13 flags were provider output failures (mostly Groq: `normalized` not a JSON object, chunks of a split document disagreeing), about 10 were convention differences (officer title vs name, contact org vs department, how a category is quoted, `relative_text`), and a few were real errors (Groq absent on required_documents, notice_date and submission_modes; Gemini inferring award_method from the procurement type). A cue bug (担当 inside 支出負担行為担当官) caused one flag. Gemini's free quota is 20 requests/day, 503s occurred, and Groq was only called after Gemini answered.
Decision:
- **Text fields may be `see_other_document`.** The label format already stored the ref as `normalized: {"ref": {...}}` for every field; the bug was in the answer parser (`model.from_row`), which dropped `normalized` for every text field. Fixed there; the ref is stored the same way as for structured fields. The 36 reviewed sv1 lines still validate; F-0029 imported.
- **Conventions** in `docs/labeling_guide.md`, each with a pilot example; its rule block is sent word for word in every sv2 prompt (editing it means bumping `PROMPT_VERSION`).
- **Per-field schema.** The answer is `{"fields": {id: entry}, "normalized": {id: value}}`: one shared entry (status, ref, value_ja, value_en, citations, reason) by `$ref`, and each structured field's own schema derived from its pydantic model, made strict (all properties required, no extra keys, no `not_stated` or `see_other_document` inside a value, nullable via `anyOf` null). Both providers' docs (read 2026-10-03) list objects, enums, `anyOf`, `["type","null"]` and `$ref`/`$defs` for their strict modes (Groq `strict: true` on gpt-oss-120b; Gemini `responseJsonSchema`, which warns that very large schemas may be rejected). **Not checked by a call:** whether either accepts this schema. A `normalized` sent as a string is parsed once more before it fails.
- **Groq gets field groups.** Rules + guide + field help + schema are about 6,100 estimated tokens for a notice, more than Groq's 8,000-token request allows with an output allowance. A request is now a part: a group of fields asked about one chunk. Per document the planner picks the number of groups with the fewest estimated tokens in total, each request with room for at least 800 tokens of text; Gemini always gets one group. Cost: the sv2 pilot plan is 18 Groq requests and about 118k estimated tokens for the 5 pilot documents, where sv1 planned 12 and about 76k.
- **Chunk merging.** Lists: union of the parts' items, deduplicated by citation overlap and value. Scalars: parts that agree are one answer, the one cited under the field's heading cues best is kept; parts that disagree become `alternatives`, the field is flagged ("parts of the document give different answers") and the reviewer sees both; never a schema failure. Absent in one part and present in another is present.
- **value_in_citation** accepts a quote shortened with … or ... when its pieces occur in order; the prompt forbids ellipses and status tags in title.
- **Heading cues** (soft check and the both-absent trigger) count only in section titles and the first 15 characters of a sentence, and not in the middle of a longer word (a kanji or katakana on both sides). For the both-absent trigger, cues of 3 characters or fewer count only as a whole heading.
- **Providers run independently.** Each has its own queue over the selected documents (its resume state is its raw cache file); a daily cap or outage stops only that provider. A document resolves when both answers are complete. `status` shows per-provider progress and today's usage.
- **One ledger for every request** (`usage.jsonl`): labeling calls and retries (`label`), probes (`probe`, new command) and key checks (`keys`), with the outcome (`ok`, `http_503`, `http_429`, `network`, ...). Failures count against the day's request budget, since Google does not document whether a 503 counts.
- **Backoff:** 503 and other 5xx, per-minute 429 and network errors wait 30, 60, 120, 240 s (or Retry-After) for up to 5 tries, then the part is `provider_unavailable`, the queue moves on, and the next run retries it.
- **No second Gemini model.** `gemini-3.7-flash` is listed as free on the pricing page (read 2026-10-03), but the docs do not say whether it has its own daily quota (limits are per project and shown only in AI Studio), or whether it shares capacity with 3.8 during an outage. Skipped.
- **Review export:** A and B carry no provider names; `export/mapping.json` records them per item. List fields get C, the union of A's and B's items; the reviewer can answer `accept C`. Import records `provenance.reviewed_choice` (provider, `union` or `custom`) and a line in `reviews.jsonl`; `review-stats` prints, per provider and field type, how often its candidate was right. A custom answer may cite any Japanese sentence of the document (it already could; now tested and said in the answer format). Imported items keep the prompt version they were made with.
- **Comparison mode:** a document that already has labels is never resolved again; `run` compares its new answers with the existing labels and writes only `eval/reports/silver_pilot_sv2.md` (plus the raw cache and ledger).
Consequences: Groq stays the bottleneck and costs more per document. The pilot A/B mapping was recovered after the fact (D-47). 503 counts in `silver_pilot.md` are reconciled there: 16 HTTP 503 and 1 HTTP 429 (daily quota) among Gemini's 17 failed requests.

## D-48: sv2 pilot results, and what changed around it
Date: 2026-10-03
Status: accepted for the code changes below; the fixes for Gemini and Groq are proposals (report `eval/reports/silver_pilot_sv2.md`), not decided
Context: The sv2 pilot (5 open dev documents, `--max-calls 40`) resolved 1 document. Gemini's `responseJsonSchema` returned HTTP 400 INVALID_ARGUMENT for the 21- and 23-field schemas (bid instructions, notices) and accepted the 6-field one (spec). One extra request with the 23-field schema and no document text gave the same 400 with the generic message "Request contains an invalid argument", so the schema itself is the trigger; the keyword set is the same as the accepted schema, only the size differs (39 vs 6 `anyOf`, depth 14 vs 11). Groq's strict mode accepted every grouping, but 4 of 19 parts came back `json_validate_failed` (the answer broke the schema), which the pipeline treats as a final failure.

- **Labeling guide (prompt sv2, no sv2 call had been made):** org is the body that issues the notice in its own name (a ministry, a 庁, a prefecture or a city), everything below it is department (和歌山県 / 会計局会計課, doc `081d27569eac` p1_s1); issuer_org follows the same rule. required_documents lists 入札書 whenever the notice mentions the bid form in any way, not for a proposal competition that never does.

- **Error messages kept:** a 4xx keeps the provider's message (redacted, 200 characters), so the next 400 says why.

## D-49: Gemini answers in JSON mode, with one repair request (fix A)
Date: 2026-10-03
Status: accepted (Yasharth's decision after the sv2 pilot, D-48)
Context: Gemini's strict schema mode (`responseJsonSchema`) refused the sv2 schemas for notices (23 fields) and bid instructions (21 fields) with HTTP 400 INVALID_ARGUMENT, and accepted the 6-field spec schema (D-48). Fix B (field groups) would cost 2 to 4 requests per document out of 20 a day.
Decision:
- **No strict schema for Gemini** (`ProviderCfg.strict_schema = False`). The request keeps `responseMimeType: application/json` and drops `responseJsonSchema`. The prompt describes the answer: the envelope (`{"fields": {...}, "normalized": {...}}`, one entry per asked field) and one compact form per field, generated from the pydantic models in `fields.py` (`prompt.field_form`, for example `{"status": required|waived|waived_with_proviso, "rate_percent": number|null}`), so the forms cannot drift from the schema. The hand-written forms in `FIELD_HELP` were replaced by one-line hints. The same field list goes to every labeler (Groq and the local model still get their strict schema as well). The forms are also printed in `docs/labeling_guide.md`; a test fails if the two differ.
- **Our checks replace the schema** (`checks.shape_errors`): the answer must be JSON, have the envelope, list every asked field, and each entry must pass `schema_valid` (status, ref, `normalized` against the field's model, the label-format rules). Content checks (citations, quotes, converters, era, weekday) are not part of it: they stay with the consensus, so a repair never gives Gemini a second try at content that the other labeler does not get.
- **One repair request** when the first answer has shape problems: the same system and user prompt, Gemini's answer as a `model` turn, and a user turn listing the problems (at most 40 lines) and asking for the whole answer again. The answer with fewer problems is kept (an unparseable repair never replaces a parseable first answer); both the problems before and after are stored in the raw cache (`repair`). The repair is an ordinary request: it goes through the limiter, the ledger and `--max-calls`. If the repair request itself fails, the first answer is kept. An answer cut off by the output cap fails without a repair.
- **One request per document.** Fields are split into two groups only if the estimated answer (`est_output`) would pass Gemini's output cap (16,384 tokens, thinking included). On the dev set that never happens: the largest is 23 fields, about 3,360 estimated tokens (`plan_parts`, counted in the sv3 report).
Consequences: Gemini can label every document type again. Each repair costs one of the 20 requests a day; the sv3 report gives the observed repair rate and the projection. Gemini's `normalized` values are no longer guaranteed by the provider; a shape problem the repair does not fix becomes a `schema_valid` failure and a flag, as for any labeler. The estimate (`overhead`) still counts the schema for Gemini, so its input estimate runs a little high.

## D-62: The gold daemon and the gold export policy; the tier 1 field list
Date: 2026-11-16
Status: accepted (Yasharth's task of 2026-11-16; the daemon is built, no run has been started)
Context: D-61 wants every tier 1 field of the gold set reviewed and left "which fields are tier 1" for before wave 1. Labeling a wave takes several Gemini quota days (20 requests a day on this account, Pacific day, failures counted: D-56, D-57), so the run has to wait, resume and stop safely without Yasharth watching it.
Decision:
- **Tier 1 fields** are these ten concepts, mapped to schema 1.0.0 field ids (`daemon.CONCEPTS`, checked against `config.TIER1` and `FIELD_IDS` by `daemon.tier1_problems`; a concept without a real id, an id used twice or a mapping that differs from `config.TIER1` stops the daemon and is listed, never guessed): submission deadline(s) = `deadlines` (the list of dated events: bid, mail arrival, electronic, opening, question, briefing, document request; `delivery_deadline` is a different field, the delivery date of goods, and is not tier 1); submission method(s) = `submission_modes`; bid bond = `bid_bond`; performance bond = `performance_bond`; eligibility = `eligibility`; unified qualification = `unified_qualification`; tax basis = `tax_basis`; spec access = `spec_access`; procurement type = `procurement_type`; award method = `award_method`. This is the list `config.TIER1` already held for the export order and the single-source exclusion (D-52); it is now also the gold review list.
- **Gold export policy** (`daemon.gold_mark`, applied when a gold document resolves, through the `mark` hook of `run.resolve_docs`): every flagged field is exported; every accepted tier 1 field is exported even when the labelers agreed (item kind `spot`, reason "gold: tier 1 field, always reviewed"); and a 20% sample of the other accepted fields (`sha256(20261016:doc_id:field)`, the gold set's seed, so two runs pick the same fields). The D-43 5% spot-check does not apply to gold documents. Rule-absent fields (field not applicable to the document type) are never exported.
- **The daemon** (`uv run python -m eval.silver daemon --gold --wave N [--yes --max-calls N] [--plan]`, `eval/silver/daemon.py`) is a loop around `Pipeline.label`, `run.resolve_docs` and `review.export`, not a second pipeline. It takes the wave's documents with no resolution yet (no decisions file and no resolved lines), labels with Gemini and the local Qwen3.5-9B (Groq is never used), and refuses any document that is not `license_class` open in the manifest or whose organization is not in the dev split of `splits.json`, even when `gold_set.json` lists it (checked twice: when the wave is read, and before every labeler call). A provider at its daily cap (the ledger, Pacific day for Gemini) is set aside and the other goes on; when nothing else can be asked the daemon sleeps until the earliest reset (the provider's midnight in its quota time zone plus 5 seconds), in steps of 60 s that check the stop file, then asks again. Every answered part is cached, so a restart repeats no request; a labeler whose parts are all cached is not even built.
- **Hard stops, each one logged:** `--max-calls N` (required with `--yes`; counts every request including retries, repairs and local ones); three failures in a row from one provider (any `ProviderError`; a daily-quota 429 does not count, it is a cap); the laptop on battery (`pmset -g batt`: it pauses, checks every 60 s and goes on when plugged in; it does not exit); the stop file `data/cache/labeling/STOP`, checked before every request and while sleeping. A start is refused while `STOP` exists, so remove it first. `data/cache/labeling/daemon.pid` holds the process id; a start is refused when that process is alive (`os.kill(pid, 0)`), a stale file is replaced, and the file is removed on exit. Watch or stop the daemon by process id only (CLAUDE.md).
- **Without `--yes` the command is `--plan`**: it prints the tier 1 mapping, the wave's documents, requests still to make per labeler (cached parts excluded), each cloud provider's requests left today and its next reset, the export it would make, the hard stops and the state of the pid and stop files. It reads files only: no cloud request, no local model request (the local server is never started), no file written. Cloud calls need `--yes`, as CLAUDE.md requires.
- **Export:** when the daemon ends (wave done, a hard stop, or the stop file) it writes `data/cache/labeling/export/batch-w<N>-NN.md` for the resolved documents of the wave, in the existing batch format with "(gold wave N)" in the title; it replaces only that wave's own files, and the plain `export` now replaces only `batch-NN.md`. Nothing is imported; Yasharth runs `import`.
- **Log:** `data/cache/labeling/daemon.log`, one line per event: time, event, provider, count (requests), secs, document id prefix (12 characters). No document text, no error text, no key.
Consequences: (1) Documents of a wave that were resolved earlier under the D-43 policy (wave 1 has two from dev day 1: 136dfba9ee59, 84e9d0c8325c) are not labeled again, but on every start the daemon resolves them again from the raw cache with the gold policy (`Daemon.regold`, no request; a reviewed line is never replaced, the sample is a hash so repeating changes nothing). Yasharth chose this on 2026-11-16 over leaving the gap. The plan lists how many tier 1 fields of such a document are not in review yet. (2) Tier 1 items that the labelers agreed on are kind `spot`, so `status`' "consensus spot-check ... % silver error estimate" now mixes them with the 5% sample; read `reviews.jsonl` by field for the gold numbers. (3) A batch file is rewritten by the next daemon end, so a wave's batches should be answered after the daemon has stopped. (4) The daemon's estimate of requests is the cached-aware count of `run.price`; retries, repairs and failures cost more and failed Gemini requests count against its 20 a day.
